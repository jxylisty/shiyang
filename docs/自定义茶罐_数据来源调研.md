# 调研：自定义茶罐的外部数据来源

> research-scout @ 2026-11-05
> 全部结论基于 2026-11-05 当日实测（curl 直连 + 接口调用 + 论文摘要核对）。
> 凡未实测的一律标注「未验证」，不写估算值。

---

## 一句话结论

**谨慎做，且必须「专业 API 打底 + AI 只做翻译层」**。
实测结论：**HERB（herb.ac.cn）有真实可调用的非鉴权接口，34/34 味本地药材精确命中，28 味本地没有的常见养生材料命中 25 味**——「药→成分→靶点→文献」这条链可以在不注册、不付费的情况下打通。
但**不能走「AI 纯联网搜索」路线**：功效描述是英文直译、无剂量、无含量数据，AI 自由发挥必然编造。
另有一条**许可红线**：HERB 是 CC BY-NC（禁商用），TCMSP 是 ODbL（可商用但要求同源开源）——大创结题若涉及商业化，须提前定调。

**撞车档位：绿（无有效竞品）**，但须回答「为什么没人做好」——见文末「空白地带」。

## 五、两条路线的对比与推荐

### 路线 A：AI 联网搜索（DeepSeek Search / 通用联网模型）

**实测事实**：
- DeepSeek 已上线官方 Search/Fetch API：`POST https://api.deepseek.com/v1/tools/search`（body: `query`、`count`、`need_content`）、`POST /v1/tools/fetch`（body: `url`）。计费 **$0.75 / 1,000 次成功请求**，Search 100 QPS / Fetch 25 QPS。
  [来源：DeepSeek Search & Fetch API 文档](https://api-docs.deepseek.com/guides/search)
- 返回字段含 `rerank_score`（0-3，「1.5 以上视为高质量」）与 **`authority`（0-4，3+ 为高权威）**——这是可直接拿来做来源打分的信号。

**能力边界（明确）**：
- ✅ 擅长：把「小红书那段话」解析成结构化药材+克重；把「清热明目」翻译成用户能懂的话；解释为什么两味药搭配。
- ❌ 不能做：给出成分含量百分比、给出靶点 P 值、判断「这个方子是否真的有效」。这些**没有任何搜索摘要能提供**，模型只能编。
- ⚠️ 已知失效点：本机 `api.deepseek.com` 无 key 请求返回 401（正常），但 **OpenAlex、Semantic Scholar、Wikidata、Open Targets 在本网络全部连接失败**（OpenAlex 000 / S2 429 / Wikidata 000 / Open Targets 000），所以「让 AI 自己去权威库查」这条在本机环境**不可靠**，必须由后端直连。

### 路线 B：调用专业数据库 API（HERB 为主）

**实测事实**（这是本次调研最重要的产出）：
- HERB 三个接口全部可用，无需 key、无需注册、响应 0.1s（搜索）/ 0.6-0.8s（详情，单条 400-700 KB）。
- 34 味本地药材 **34/34 精确命中**（`Chinese name` 字段完全等于输入）。
- 28 味本地没有的常见养生材料 **25 味精确命中**（决明子/荷叶/玫瑰花/桂花/大枣/芡实/莲子/葛根/蒲公英/罗汉果/淡竹叶/白茅根/芦根/杜仲/无花果/牛蒡根/栀子/佩兰/砂仁/白芷/紫苏/黑芝麻/核桃仁/龙眼肉/黄芪）。
- 3 味未命中：**桂圆**（正名「龙眼肉」命中）、**苦荞**（「苦荞麦」未试）、**藿香**（有 5 个候选但无完全同名）→ 说明**必须有异名归一表**，直接字符串匹配会有 10% 左右漏检。
- 真实方子端到端跑通（决明子 10g + 菊花 5g + 枸杞子 5g + 金银花 3g）：
  | 药材 | 成分 | 靶点 | 疾病 | 文献 |
  |---|---|---|---|---|
  | 决明子 | 184 | 39 | 2,066 | 1 |
  | 菊花 | 413 | 80 | 2,380 | 5 |
  | 枸杞子 | 309 | 118 | 3,140 | 0 |
  | 金银花 | 386 | 118 | 3,095 | 1 |
  合计 1,292 条成分关系、355 个靶点关系——**这个量级已经远超本地 165 个化合物**。

### 推荐：**A+B 混合，B 为骨、A 为皮**

```
用户输入"决明子10g 菊花5g 枸杞5g"
   │
   ├─ ① LLM 解析（路线A，1 次调用）→ [{name:"决明子",g:10}, ...] + 异名归一
   │     作用仅限"文本 → 结构化"，不产出任何事实
   │
   ├─ ② HERB search_api 消歧 → HERB00xxxx      （事实层，必须来自 API）
   ├─ ③ HERB detail_api → 功效/成分/靶点/文献   （事实层）
   ├─ ④ 本地 compound 表 126 个 chembl_id → ChEMBL 实测活性（事实层，可选）
   ├─ ⑤ Europe PMC 按 HERB 给的 PubMed ID 回查（可核验层）
   │
   └─ ⑥ LLM 翻译（路线A）：把 ③ 的英文中医术语 + ⑤ 的文献结论，
          写成"这杯茶大概能帮到什么事、什么人别喝"，并逐句挂来源
```

**关键约束（写进 prompt 的硬规则）**：
1. LLM **只能改写 ②③④⑤ 返回的字段**，不得引入任何未返回的药材/成分/数字。
2. 每条功效陈述必须能指回 `HERB00xxxx` 或 `PMID xxxxx`，前端可点。
3. 剂量相关的结论一律不生成——HERB/ETCM 都**没有含量百分比**，这是本项目 `herb_compound_content` 表的独有资产（3,970 条），外部补不了。

## 六、技术可行性

| 关键难点 1：药材名消歧 | **中**。34 味本地药 100% 命中，但外部材料需异名表；「桂圆→龙眼肉」「藿香→广藿香」这类不处理就漏 | 实测 28 味新药材 25 命中，3 味靠异名 |

| 关键难点 3：英文中医术语 | **中**。HERB `Function` 是「To remove toxic heat and dispel wind-heat」这类直译，直接给用户看不懂 | 端到端实测，4 味药全部如此 |
| 关键难点 4：无含量数据 | **高，且外部无解**。HERB/SymMap/ETCM 均无「某药材含某成分 x%」的定量字段（SymMap SMIT 只有分子量/OB score，无含量） | 实测 schema |
| 所需算力/成本 | 极低。HERB 免费；LLM 按现有 DeepSeek 计费；若用 Search API，$0.75/1k 次 | — |
| 预估工作量 | **后端 3-5 人日**：`herb_service.py`（search/detail 封装 + 裁剪 + 缓存）+ `herb_alias` 表 + 超时降级。**前端不在本次范围** | — |
| 缓存策略 | 必须。药材详情对同一 HERB ID 是静态的，按 ID 落 SQLite/JSON 缓存，避免重复 700 KB 拉取 | 实测 3 次同请求均返回相同 453,774 字节 |
| 合规 | HERB 为 **CC BY-NC**：大创非商业用途可用；**若未来商业化需换源或取得授权**。TCMSP ODbL 可商用但要求衍生库同源开放 | 见 §1.1 / §3 |

## 七、撞车判定（逐项）

| 对象 | 档位 | 依据 |
|---|---|---|
| HerbiV | 🟡 部分重合 | 同为中药-成分-靶点分析、同在南京。但输入是内部 ID、输出是网络图，面向研究者；本项目输入是「网上的方子」、输出是白话。**差异点：用户层 + 白话翻译 + 剂量** |
| OpenTCM_Discovery | 🟡 部分重合 | 67 工具覆盖 `tcm_formula_analysis`（两味药成分重叠）。但需本地部署 Python+Vina、面向科研。**差异点：零部署、面向普通用户** |
| mcp-herb-tcm | 🟢 无有效竞品 | 0 star、第三方网关代理、无 UI。**但它证明 HERB 封装可行** |
| TCMNP / TCMDATA | 🟢 无有效竞品 | GPL-3.0 / 无许可证，且是分析工具不是产品 |
| 商业养生 App（竞品分析已有结论）| 🟢 | 均无分子层数据，不重复调研 |

### 「绿」档必须回答：为什么这件事还没被做好？

**三个真实原因，逐条有证据**：
1. **上游库大面积死亡或锁死**。TCMID 502、TCM-Mesh 502、TCMBank 域名全挂、BATMAN-TCM 连不上、TCMSP 检索失效+新版强制登录。**做这件事的人大多在 2021-2023 年撞死在这一步**，不是没想到，是源没了。
2. **活着的库没有「用户语言」**。HERB 有数据但功效是英文直译；SymMap 有中文性味但没有 API 只能整包下载；ETCM 有中文但接口半通。**「能查」和「能讲给人听」之间有一道翻译鸿沟**，这道鸿沟正好是 LLM 2024 年后才填得上的——**这是时机问题，不是伪需求**。
3. **没人愿意做「证据分级」这件脏活**。`mcp-herb-tcm` 的 `evidence_tier` 和本项目 `evidence_service.py` 的 A/B/C 分级是同一个洞察：**养生内容的信任问题不是「有没有数据」，是「数据是什么等级」**。做这个要逐条标注、要承认「这条只是计算预测」，很累且不涨 star，所以开源圈没人做完整。

> **风险提示（必须写进答辩）**：HERB 的 `herb_target` 是**统计富集**（带 P 值/FDR），`herb_disease` 同理。它们是「该药材的成分集合与这些靶点显著重叠」，**不是「喝了能治这个病」**。本项目红线（AGENTS.md §2.3）明确要求区分预测与事实，这一点在接入时必须原样保留 P 值并标注「统计富集，非临床证据」。

## 八、空白地带（按可行性排序）

1. **【最高】中文白话功效层**（可行性高，工作量小）
   HERB 给英文 `Function`，dayi.org.cn 给中文但无 API。**做法**：HERB 拿结构化事实 + LLM 在严格约束下翻译成中文白话 + 中文表述用 dayi 页面做人工抽检校准（不做实时抓取，避免版权风险）。这是「导师要求 3：在药材层讲清楚」的直接落点。

2. **【高】证据分级直出**（可行性高）
   HERB 的 `Experiment type`（`Clinical Experiment` 等）+ `herb_disease` 的 P/FDR + ChEMBL 的实测活性，三者天然构成 L1-L4 分级。**本地 `evidence_service.py` 已有 A/B/C 框架，只需把外部来源映射进去**，不用新造体系。

3. **【中】本地 165 成分的「外部扩样」**（可行性中）
   本地只有 165 个化合物，HERB 一味金银花就有 386 个成分关系。**不必全量入库**——只对「用户实际输入的方子」按需拉取、按需缓存，形成「本地精、外部广」的双层结构。

4. **【中】126 个 chembl_id 的实测活性补全**（可行性中）
   现成的桥：本地 126/165 成分已有 ChEMBL ID → 直接 `GET /chembl/api/data/activity?molecule_chembl_id=...`。**这是把「体外预测」升级为「体外实测」最省力的一步**，且旧文档已记录 465 条活动入库。

5. **【低】含量数据的外部补充**
   实测 HERB / SymMap / ETCM **均无含量百分比**。要补只能走文献（本项目已有 3,970 条自建）。**外部补不了，别指望**。

## 九、待确认（需要人判断或本轮未验证）

1. **HERB 的商业使用边界**。EPMC 元数据标 `cc by-nc`，但 HERB 站点本身未挂明确 license 页（`/Contact` 返回空壳 SPA）。**若项目要商业化，必须发邮件确认或换 TCMSP（ODbL）**。这是当前最大的未决合规项。
2. ~~**ETCM 的数字口径**~~ **已结（2026-11-07）**：答辩统一用 ETCM v2.0 论文原文 2,079 药材 / 38,298 成分 / 1,040 靶点 / 48,442 方剂（PMID 37425046，PMC10326295 全文核实）。原 `开源资源清单.md` 的 1,399 / 33,145 / 2,299 在 v1 与 v2.0 论文中均不存在，属错误记录已删；本表原记的 402 / 7,284 / 2,266 为 v1 首页统计条，保留作历史对照。详见本文档 §2 表下方注。
3. **TCMSP 是否彻底不可检索**。本次三种参数组合（`qr` / `qs` / 带 session cookie+token）均返回空表。可能是站点改版或需登录。**未验证**，若要依赖它需再攻。
4. **dayi.org.cn 的抓取合规性**。`robots.txt` 为 `Disallow:`（不禁止），但页面声明「未经平台允许 不得私自转载」。**建议只做人工抽检校准，不做自动化抓取**，或去函询问。
5. **SymMap 是否真无 API**。本次只确认了「批量 xlsx 可下 + 搜索页是表单」。可能存在未发现的 JSON 端点，**未穷尽**。
6. **NPASS 2026 版**（PMID 41243954）连通性未测，若需要「天然产物定量组成 + ADME-Tox」可补测。
7. **OpenTCM_Discovery 的 67 个工具是否真能跑通**。只读了 README，未实跑。若考虑直接复用它，需先验证 `tcm_check_database_status`。
