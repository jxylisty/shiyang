# 食养有据 · 数据库设计文档

- **版本**：v0.2.0（对应 `data/shiyang.db` + `data/user.db` 实际建库结果）
- **基准日期**：2026-10-26（schema 逐表核对自建库脚本与库内实际结构）
- **构建管线**：`scripts/build_db.py`（全量重建）→ `import_content.py/_batch*.py`（内容核对）→ `pregen_analysis.py`（成分分析）→ `pregen_ai_reports.py`（AI 预解读）

> 红线声明：**本平台内容为健康参考信息，不构成医疗建议，不用于诊断或治疗。** 体质判定规则依据《中医体质分类与判定》（ZYYXH/T157-2009）。

## 1. 总体架构

### 1.1 双库分离

| 库 | 角色 | 连接方式 | 重建影响 |
|---|---|---|---|
| `shiyang.db` | 知识库（方子/药材/成分/靶点/体质/预生成内容） | API 以 `mode=ro` 只读 URI 打开 | 可随时由 scripts 管线全量重建，不影响用户 |
| `user.db` | 业务库（账户/档案/收藏/打卡） | 服务层读写，WAL + 外键 | 永不重建，用户数据独立保全 |

设计动机：知识库迭代频繁（目录打标、批次导入、成分补录、预解读再生成），双库分离保证「重建方子库不丢用户数据」。

### 1.2 数据血缘

```
卫健委药食同源目录(106种) ──┐
                            ├─→ herb ←── my-asthma-system/asthma_v2.db（只读抽取）
recipes_v0.1.json(73方) ────┤     │
                            │     ├─→ rel_herb_compound ─→ compound ─→ rel_compound_target ─→ target
constitution.json(CCMQ) ────┴─→ recipe ─→ rel_recipe_material ─┬─→ herb_id
                                    ↑                          └─→ food_id ─→ food
                        constitution / constitution_food_ref / meta
                        recipe_analysis / recipe_pregen_ai / herb_compound_content（分析产物）
```

## 2. 知识库 shiyang.db（16 表，2026-10-26 实测；含归属重建新增 `rel_herb_compound_v2` 与通路分析新增 `recipe_pathway`，两张新表见 §2.2/§2.3）

### 2.1 实体表

**herb — 药食同源药材（34）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | 继承自哮喘库的稳定 ID |

| is_food_homology | INTEGER 默认1 | 药食同源标记 |

**food — 普通食材（39）**：`id` PK、`name` UNIQUE、`category`（水果/谷物/蔬菜/肉禽/水产/调味/茶叶/其他）、`nature/flavor/functions/contraindication`、`nutrient_json`（预留中国食物成分表）、`note`。性味功效标注“编目暂录，待《中华本草》核对”。

**recipe — 方子（73：茶饮44/药膳29）**

| 字段 | 说明 |

## 3. 业务库 user.db（5 表，2026-10-26 实测）

> user.db 为**活库**，各表行数随真实使用变动（如 user/constitution_record 会增长），本节只记结构不记快照行数；需要现值时用 `SELECT COUNT(*) FROM <表>` 实测。

全部 `CREATE TABLE IF NOT EXISTS`（服务启动自动迁移），存量库补列走 `user_service._migrate()` 增量 `ALTER TABLE`，连接统一 `WAL` + `PRAGMA foreign_keys=ON`。

**user**：`id` PK、`username` UNIQUE NOT NULL（3-20 位字母数字下划线）、`password_hash`（bcrypt）、`nickname`、`created_at`。

**constitution_record**：`user_id`→user(id) 外键、`main_code/main_name`（主体质）、`combined`(JSON 兼夹)、`transformed`(JSON 九维转化分)、`answers`(JSON 原始作答，复现测评用)、**`member_id`**(→family_member，T2-8 家庭代测时挂成员，本人为空)、`created_at`。索引 `idx_cr_user(user_id)`。

**family_member（T2-8）**：`user_id`→user(id)、`name`、`relation`（关系标签）、`color`（头像色）、`created_at`，**UNIQUE(user_id, name)**。家庭档案功能，成员体质记录复用 constitution_record。

**favorite**：`user_id`、`recipe_id`、`created_at`，**UNIQUE(user_id, recipe_id)** → 收藏幂等（INSERT OR IGNORE）。

**checkin**：`user_id`、`recipe_id`、`day`（本地日期 YYYY-MM-DD）、`created_at`，**UNIQUE(user_id, recipe_id, day)** → 一天一方一条。索引 `idx_ck_user_day(user_id, day)` 支撑连续打卡 streak 计算。

> 注：favorite/checkin 的 recipe_id 为逻辑引用（跨库不建物理外键），因为 recipe 表在另一库、且知识库允许重建换 id——当前以业务层保证有效性和兜底显示（`#id`）。

## 4. 设计评估（产品级/可参赛标准）

**达标项**

1. **领域建模完整**：目录→药材→成分→靶点→通路证据链 5 层全落地，配合体质-宜忌-推荐闭环，支撑“每个方子都有有效成分说明书”的核心产品叙事。
2. **读写分离与数据安全**：知识库只读 + 业务库独立 + 外键强制 + 幂等唯一约束，API 层无法破坏知识数据。
3. **溯源字段齐备**：source/reference_url/status/source_db/reference/目录批次——每条证据可回溯出处，符合科研诚信要求（参赛评审加分项）。
4. **JSON 列的取舍**：scenes/宜忌体质等低基数标签用 JSON 数组列，避免 73 方规模下的过度范式化；查询走 Python 侧过滤，规模可控（百级方子）。top_compounds 等分析快照同为 JSON——它们是整体读写的展示数据，无按字段查询需求，合理。
5. **量表/规则进 meta 表**：判定标准可追溯、可替换，与 ZYYXH/T157-2009 标准对齐。

**已知边界（登记在案，非阻断）**

1. JSON 列无法下推 SQL 过滤——方子库扩展到千级以上时需迁移为关联表或启用 SQLite JSON 函数索引。
2. user.db 的 recipe_id 逻辑引用依赖业务层校验；若引入在线管理端需加存在性校验接口。
3. 单机 SQLite 并发写入上限约百级 QPS——校内演示规模充裕；上线多实例部署时优先迁移 user.db 到 PostgreSQL（表结构可直接平移）。
4. nutrient_json 预留字段未填充（中国食物成分表接入后启用）。

## 6. 2026-11-05 扩容 schema 增量

> 依据：docs/数据扩容方案_2026-11-05.md（§2「schema 变更」与「红线」）。目标：药食同源目录 106 味全覆盖，
> 新药材从 herb.ac.cn（HERB）拉成分（HBIN ID）与成分-靶点关联（HBTAR，含 P-value/FDR）。
> 基线（2026-11-05 实测）：herb 34 / compound 165 / target 2,807 / rel_herb_compound 201 / rel_compound_target 12,168。
> 执行方式：**只加列、只建索引，不改任何数据行**；迁移代码在 `scripts/_migrate_20261105.py`，
> 数据灌入由后续 `scripts/import_herbs_20261105.py` 负责。本节记录的是 DDL 与落位决定，不是灌库结果。

### 6.1 DDL：herb 表加三列（幂等 ALTER）

SQLite 的 `ADD COLUMN` 只允许加**可空列**（不允许 NOT NULL 无默认 / UNIQUE / PK），且存量 34 味这些列本无值——可空是唯一诚实口径：

```sql
ALTER TABLE herb ADD COLUMN source TEXT;          -- 数据来源，如 'herb.ac.cn HERB003070'（机构名+ID，沿用 recipe.source 惯例）
ALTER TABLE herb ADD COLUMN reference_url TEXT;   -- 详情页 URL，可点开溯源
ALTER TABLE herb ADD COLUMN added_batch INTEGER;  -- 入库批次，本批=20261105；存量 34 味由灌库脚本补标同值
```

**配套索引**（partial index 需 SQLite 3.8+，本机 3.45.3 已验证）：

```sql
-- 「成分→药材」反向查询：扩容后 v1 关联从 201 条涨到万级，
-- 原 UNIQUE(herb_id,compound_id) 隐式索引只覆盖正向（药材→成分）
CREATE INDEX idx_rhc_compound ON rel_herb_compound(compound_id);

-- herb.ac.cn 来源的成分-靶点关联幂等约束：同一 (成分, 靶点) 在该来源只允许一条，
-- 灌库用 INSERT OR IGNORE 借它去重。partial 条件限定 source_db='herb.ac.cn'，
-- 存量 12,168 条（source_db 全为 NULL）完全不受影响
CREATE INDEX ux_rct_hbtar ON rel_compound_target(compound_id, target_gene)
    WHERE source_db = 'herb.ac.cn';
```

**明确不加索引的列**：`herb.source / reference_url / added_batch`——全表仅 106 行，追溯查询低频且无覆盖索引必要，加了负收益；`target.gene` 是主键自带索引；`herb.name` 已有 `idx_herb_name`。

**语法验证命令**（内存库，CREATE + ALTER + 两个索引跑通即通过；2026-11-06 在 SQLite 3.45.3 实测 OK）：

```bash
python -X utf8 -c "
import sqlite3
con = sqlite3.connect(':memory:')
con.executescript('''
CREATE TABLE herb (id TEXT PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE rel_herb_compound (id INTEGER PRIMARY KEY AUTOINCREMENT,
    herb_id TEXT REFERENCES herb(id), compound_id TEXT,
    UNIQUE(herb_id, compound_id));
CREATE TABLE rel_compound_target (id INTEGER PRIMARY KEY AUTOINCREMENT,
    compound_id TEXT, target_gene TEXT, source_db TEXT);
''')
con.execute('ALTER TABLE herb ADD COLUMN source TEXT')
con.execute('ALTER TABLE herb ADD COLUMN reference_url TEXT')
con.execute('ALTER TABLE herb ADD COLUMN added_batch INTEGER')
con.execute('CREATE INDEX idx_rhc_compound ON rel_herb_compound(compound_id)')
con.execute(\"CREATE INDEX ux_rct_hbtar ON rel_compound_target(compound_id, target_gene) WHERE source_db = 'herb.ac.cn'\")
print('OK, herb cols:', [r[1] for r in con.execute('PRAGMA table_info(herb)')])
"
```

**兼容性核查（2026-11-06）**：backend 全部 herb 查询均为显式列名，无 `SELECT * FROM herb`（唯一一处 `SELECT *` 在 user.db 的 herb_cache，与本库无关）——加列对后端零影响。

### 6.2 ID 命名决定（关键决定 + 理由）

| 对象 | 决定 | 理由 |
|---|---|---|
| **herb.id（新药材）** | 直接用 **HERB ID**（如 `HERB003070`），与存量 `ccTCM%` 共存混用 | ① 存量 34 味的 `ccTCM%` 来自哮喘库 ccTCM 数据库，新 74 味在 ccTCM 无 ID，**伪造 `ccTCM%` 前缀=编造 ID，违反数据真实铁律**；② HERB ID 是权威库稳定 ID，当主键天然可溯源（`source` 字段照方案仍记 `herb.ac.cn HERBxxxxx`，冗余但便于统一展示）；③ 后端无任何按 id 前缀分支的逻辑（2026-11-06 全文核查），TEXT 主键混用无冲突 |
| **compound.id（新成分）** | 直接用 **HBIN ID**，与存量 `ccMon%` 共存 | 同上：不伪造 `ccMon%` 前缀。存量 `ccMon%` 全部带预测列（prob/radar），新 HBIN 行预测列全 NULL，一查 id 前缀即可区分口径 |
| **target.gene（新靶点）** | 用 **HBTAR 返回的 gene name**，不用 HBTAR 数字 ID | `target` 表主键是 `gene TEXT`，存量 2,807 行全按 gene name（如 PTGS2）存；证据链端点 `JOIN t.gene = rt.target_gene` 也按 name 连。用数字 ID 会让同一靶点存两行，破坏主键语义 |
| **关联表** | 新药材成分关联写 **rel_herb_compound（v1）**；`v2/v3` 不动 | 方案定稿口径：v2/v3 是「归属重建」asthma 口径专用表（见 §2.2 与 docs/归属重建报告.md），新药材数据不属于该口径。**注意**：后端证据链等读 v3 且注释 v1「禁用」（见 6.5 风险 1），本批数据因此在这些端点不可见——这是本阶段的明确取舍，不是缺陷 |

**判重与打通**：按 `herb.name` 判重 upsert（方案红线）。存量 34 味中 32 味精确命中目录、生姜/陈皮以异名命中（2026-11-06 实测），**这 34 味不新插行**，只补标 `added_batch=20261105` 与 `source/reference_url`（若拉到数据）。扩容后 `rel_recipe_material` 中 11 种 `herb_id IS NULL` 的目录药材（决明子/枣/芡实/荷叶/莲子/覆盆子/赤小豆/铁皮石斛/鲜芦根/黑芝麻/龙眼肉）可按正名/异名映射回填 `herb_id`——注意「枣→大枣」「鲜芦根→芦根」需走异名映射，回填前先核对 `herb.name` 确实入库。

**compound_count 重算**（灌库收尾执行，属数据回填、不属于 schema 迁移）：

```sql
-- 统一为「本库 rel_herb_compound 口径」。存量值原为 asthma_v2 全库口径，重算后
-- 与本库 v1 行数一致，列表排序（ORDER BY compound_count DESC）语义更诚实
UPDATE herb SET compound_count =
    (SELECT COUNT(*) FROM rel_herb_compound WHERE herb_id = herb.id);
```

**compound（新插，预计数千行）**：`id`=HBIN ID；`name`/`smiles`/`mw` 来自 HERB summary（`Molecule smile` 字段）；`logp` HERB 无则 NULL；**`prob_cctcm`/`prob_herb`/`radar_*`/`ad_*`/`chembl_*`/`prob_indep` 全部 NULL（方案红线：不给新成分跑模型）**；`target_count` 灌库后按 rel_compound_target 计数回填（与 herb.compound_count 同理，也可先 NULL 由查询端实时 COUNT——**决定：回填**，保持「列表排序读列、详情页读关联」的既有语义）。

**target（新插行）**：`gene`=HBTAR gene name；**gene 为空的行跳过不入库并计数记录**（不造占位符）；`target_type` 留 NULL（HBTAR 关联行无类型信息，**不冒充 'Protein'**——证据链端点过滤 `target_type='Protein' AND species='Homo sapiens'` 会自然排除它们，属预期）；`species` 按 HBTAR 提供填，未知时写 `'未知(herb.ac.cn)'`（方案红线）。同一 gene name 已在存量（如 PTGS2 已有 2 条）则不重复插行、只新增 rel 关联。

**rel_herb_compound（新插）**：`herb_id`=HERB ID、`compound_id`=HBIN ID，`UNIQUE(herb_id,compound_id)` + INSERT OR IGNORE 保证幂等。新成分-新药材用 name 对不上时宁可不插（数据真实铁律）。

**rel_compound_target（新插）**：`compound_id`=HBIN ID、`target_gene`=gene name；`activity_type`/`activity_value`/`activity_unit` 填 NULL——HBTAR 给的是**统计显著性（P-value/FDR），不是 IC50/Ki 类活性值**，塞进 activity_value 会伪造活性数据；**P-value/FDR 记入 `reference` 列**，格式 `herb.ac.cn HBTAR: P=3.2e-05, FDR=0.0011`（结构化程度足够人工核查，避免为两列建新表偏离最小增量）；`source_db` 统一填 `herb.ac.cn`（触发 6.1 的 partial UNIQUE 幂等索引）。

### 6.4 索引清单增量（对应真实查询）

| 索引 | 对应查询 | 收益 |
|---|---|---|
| idx_rhc_compound | 灌库判重 `SELECT 1 FROM rel_herb_compound WHERE compound_id=?`；未来成分详情「含此成分的药材」`SELECT herb_id FROM rel_herb_compound WHERE compound_id=?` | 万级关联下反向查询从全表扫描变索引点查 |
| ux_rct_hbtar（partial UNIQUE） | 灌库幂等 `INSERT OR IGNORE INTO rel_compound_target(compound_id,target_gene,...) VALUES (...)` | 数据库级去重保证，第二遍灌库 0 变更 |

### 6.5 风险与需对齐的点

1. **v1/v3 口径张力（需产品层确认）**：backend 三处归属查询读 v3 且注释 v1「错乱表禁用」（main.py 证据链、explain_service、rag_service），本批新数据写 v1 后**不会出现在证据链/解读端点**。本阶段不修改 backend（边界），若后续要新药材上证据链，需后端改为 `v1 UNION v3` 或按 added_batch 区分——已列入 D4 核查项的关注面，非本迁移职责。
2. **同名化合物重复**：同一化合物可能同时存在存量 `ccMon%`（带预测）与新 `HBIN%`（预测 NULL）两行（如柚皮素）。本阶段**不做跨库自动合并**——合并需逐条人工比对 SMILES，自动按 name 合并曾在本项目造成系统性错配（docs/归属重建报告.md 教训）。展示层需容忍同名两条（D4 核查项）。
3. **recipe_analysis / recipe_pregen_ai 不覆盖新药材**：两表快照只服务 73 方（69 行），新药材不在方子里，天然不受影响；`compound_map`、`recipe_pathway` 同理不动。
4. **锁表风险**：SQLite ALTER TABLE 加列在表小时瞬间完成；灌库脚本与运行时 API 并发时靠 `busy_timeout=5000` 等待，且运行时 API 是 `mode=ro` 只读连接，不产生写锁冲突。建议灌库在停服窗口或低峰执行。
5. **回滚方案**：迁移只加列/建索引。列多余无害可保留；如需彻底回滚，`ALTER TABLE herb DROP COLUMN`（SQLite 3.35+ 支持）+ `DROP INDEX idx_rhc_compound / ux_rct_hbtar`；极端情况整库恢复迁移前备份（`shiyang.db.bak-migrate-<时间戳>.db`，由迁移脚本自动生成）。

### 6.6 迁移脚本与执行顺序

脚本：`scripts/_migrate_20261105.py`（纯函数 `migrate(db_path)`，不执行灌库）。

- 备份：WAL checkpoint 后 `shutil.copy2` 带时间戳复制（`data/shiyang.db.bak-migrate-YYYYMMDD_HHMMSS.db`），每次运行新文件、永不覆盖。
- 幂等：每条 ALTER 前查 `PRAGMA table_info(herb)`、每条 CREATE INDEX 前查 `sqlite_master`，已存在即跳过；并发兜底捕获 duplicate column/already exists。
- 返回：`{added_columns, added_indexes, before, after, row_consistent, backup_path, batch}`，行数不一致即抛错回滚提示。
- 执行顺序：`migrate()` → `import_herbs_20261105.py`（灌 herb/compound/target/关联）→ compound_count/target_count 回填 → `check_consistency` 一致性校验。
