# 拍照识药 · 技术方案调研

> 调研日期：2026-11-06　调研人：AI agent（team-lead 调度）
> 背景：组员提出「支持拍照上传图片，避免用户手动输入」——这是产品走向移动端应用的关键一步。
> **本文所有数字均为本机实测，非推测。**

## 一、结论先行

**选多模态视觉模型，不做独立 OCR 引擎。**

理由：多模态模型一个接口同时解决两类需求，而 OCR 只能解决其中一类：

| 用户实际会拍的东西 | 需要的能力 | OCR 能做吗 | 视觉模型能做吗 |
|---|---|---|---|
| 桌上的药材实物（当归、黄芪…） | 图像识别 | ❌ 完全不能 | ✅ |
| 手写的方子 / 药方纸条 | 文字识别 | ✅ | ✅ |
| 手机上别人的方子截图（小红书等） | 文字识别 | ✅ | ✅ |
| 药盒包装（品名+规格） | 文字识别 | ✅ | ✅ |

OCR（PaddleOCR/Tesseract）只认字不认物，而用户最想拍的恰恰是「这味药是什么」。
单独接 OCR 引擎还要多一套依赖 + 部署成本，收益却只是视觉模型的一个子集。

## 二、实测数据（本机 ZeroGate 网关，`http://127.0.0.1:7863/v1`）

### 2.1 模型可用性（同一张金银花图）

| 模型 | 耗时 | 结果 | 判定 |
|---|---|---|---|
| `glm-5v-turbo` | 2.3s | 金银花 | ✅ 可用 |
| `qwen3-vl-235b` | 2.0s | 金银花（忍冬） | ✅ 可用 |
| `doubao/doubao/vision` | 5.9s | 金银花 | ✅ 可用（走豆包桥，较慢） |
| `qwen3.8-flash` | 0.2s | HTTP 502 | ❌ 不可用 |
| `gemini-3-flash` | 20.4s | HTTP 500 | ❌ 不可用 |

> 注：`doubao-vision-bridge` skill 记录「qwen3-vl-235b 返回空 content」，本次实测已恢复正常，
> 说明是该桥接服务的瞬时状态，不作为排除依据。但为稳妥，主选 `glm-5v-turbo`。

### 2.2 识别准确度（8 味药材，原图）

| 药材 | glm-5v-turbo | qwen3-vl-235b |
|---|---|---|
| 陈皮 | ✅ 陈皮 | ✅ 陈皮 |
| 茯苓 | ✅ 茯苓 | ✅ 茯苓 |
| 山楂 | ✅ 山楂 | ❌ 山茱萸 |
| 甘草 | ⚠️ 不确定（诚实） | ⚠️ 不确定 |
| 黄芪 | ✅ 黄芪 | ✅ 黄芪 |
| 决明子 | ✅ 决明子 | ❌ 花生叶 |
| 菊花 | ✅ 胎菊（更精确） | ✅ 胎菊 |

**glm-5v-turbo 7/7 正确或诚实弃权，qwen3-vl-235b 5/7。选 `glm-5v-turbo` 为主模型。**

### 2.3 OCR 能力（合成药方图）

三个模型都能准确抄出「金银花 10g 菊花 5g / 枸杞 8g 陈皮 6g / 甘草 3g」，格式保留完整。

### 2.4 ⚠️ 关键风险：降质图准确度骤降

把黄芪图做**旋转 12° + 缩放 + JPEG q45**（模拟手机随手拍）后：

| 模型 | 结果 | 实际 |
|---|---|---|
| glm-5v-turbo | 白芍 (0.9) | 黄芪 |
| qwen3-vl-235b | 牡蛎 (0.85) | 黄芪 |

**两个模型都错了，而且置信度还很高（0.85–0.9）。**
这是本方案最重要的设计约束——**绝不能「AI 说了算」**，必须：

1. **返回多候选**（Top 3），让用户点选确认
2. **置信度不可信**，不能用来做「自动采纳」的阈值
3. **候选必须过本地知识库校验**，不在库里的名字不展示
4. **界面明确写「AI 识别，仅供参考，请自行核对」**

## 三、方案设计

### 3.1 数据通路

```
用户拍照/选图（前端）
  └─ POST /api/v1/custom-recipe/recognize-image  (multipart 或 base64)
       ├─ 图片校验：大小 ≤ 8MB、MIME 白名单、转 RGB 压缩
       ├─ 调 ZeroGate glm-5v-turbo（OpenAI 兼容 vision 格式）
       │     prompt 要求严格 JSON：{items:[{name, grams?, confidence}], type:"herb|text|unknown"}
       ├─ 本地复核：每个候选名过 _name_exists_locally()（知识库 + SymMap）
       │     ├─ 命中 → 回填标准名 + 性味归经功效（复用既有 enrich 逻辑）
       │     └─ 未命中 → 标记 unverified，仍返回但提示「数据库无记录」
       └─ 返回 {items:[...], unverified:[...], image_kind, disclaimer}
```

### 3.2 与前序功能的衔接

识别结果直接复用已有的药材输入流程：
- `items` 里的药材名 → 填入 `customHerbs`（和粘贴解析同一套 UI）
- 用户确认后再走 `/custom-recipe/analyze`
- 数据库没有的药 → 已有的 `web-lookup` 联网兜底（导师要求的那条链路）

**拍一张照片 → 识别 → 用户勾选 → 分析 → 联网兜底，一条链路贯通。**

### 3.3 两种识别模式（同一次调用返回）

模型在 prompt 约束下自行判断图片类型：
- **实物药材照** → 返回药材候选（带克重则一并提取）
- **药方文字/截图** → 返回识别出的药材 + 克重
- 两者混合（如药方旁边摆着药材）→ 都能处理

### 3.4 隐私

图片只在服务端内存中处理，**不落盘、不入库、不写日志**。
如需缓存识别结果，只存「识别出的药名」不存图。

## 四、为什么不选其他方案

| 方案 | 否决理由 |
|---|---|
| PaddleOCR / Tesseract | 只能认字，不认药材实物；还要装额外依赖（模型文件几十 MB） |
| 云厂商 OCR API（百度/腾讯） | 需要真实付费 key，违反 `ai-key-policy` 铁律；且同样不认实物 |
| 专用药材识别模型（自训练） | 没有标注数据集，训练成本远超本阶段收益；模型泛化能力反而不如通用 VLM |
| 本地 small VLM（如 Qwen2-VL-2B） | 本机无 GPU 推理环境，CPU 推理 400×400 图要几十秒，体验不可接受 |

## 五、验收标准

1. 上传一张真实药材图，返回候选列表（含标准名、置信度、是否已入库）
2. 上传一张药方文字图，能提取「药名 + 克重」
3. 识别失败/不在库时不编造，明确提示
4. 前端可拍照、可拖拽上传、可点选候选填入
5. 单次响应 < 15s（实测单模型 2–4s，留余量）

## 六、已知限制（写进产品文案）

- 切片/粉末形态的药材（甘草片、白术粉）难以辨认，模型会诚实弃权
- 光线差、模糊、遮挡会导致误判（实测降质图必错）
- 易混淆品种（山楂 vs 山里红、决明子叶 vs 番泻叶）需用户自行核对
- **平台不对识别结果负责，仅作为输入辅助**
