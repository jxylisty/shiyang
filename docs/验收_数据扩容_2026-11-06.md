## 总体结论

**能用。扩容后主链路可用，但有 1 个 P1 阻断、4 个 P2 体验问题、3 个 P3 细节问题。**

最大风险：**本地知识库已有 105 味药材和 5,643 成分，但「自定义鉴方」功能只认 HERB 搜索 API，遇到 HERB 搜不到的药材（如槐米、灵芝、天麻等大量目录药材）直接报「未找到」，完全浪费了本地已有的成分/靶点数据**。这是本次扩容验收中最核心的缺口——数据进了库，但核心入口之一看不见。

| 级别 | 数量 | 代表问题 |
|---|---|---|
| P0 阻断 | 0 | — |
| P1 严重 | 1 | 自定义鉴方对 71 味本地已有数据的药材报「未找到」（HERB search API 搜不到） |

**P0/P1 清单摘要：**
- **[P1] 自定义鉴方对 71 味目录药材报「未找到」——本地明明有完整成分/靶点数据**
  - 核心原因：`analyze_recipe` / `get_herb_detail` 只走 HERB 搜索 API，本地 shiyang.db 只用于「补中文性味」（`_enrich_with_symmap`），**完全不作为成分/靶点来源**。
  - 实测：蒲公英（HERB 有）→ ok，槐米（HERB search 搜不到但本地有 179 成分+靶点）→ not_found。
  - 证据：`herb_service.py` `_herb_id_from_search()` 只调 HERB search_api；本地 `rel_herb_compound` 105 味全部有成分，但该路径未被使用。

## 逐路径结果

### A. 全局搜索（通过，有 P3 体验问题）

- 搜索「蒲公英」「槐米」「灵芝」「天麻」「葛根」均返回药材结果，matched_by 字段准确（名称/功效等）。

- 成分搜索：搜「芦丁」/「rutin」不返回成分（设计预期：搜索只返回带 prob_cctcm 的成分，共 165 个；新成分无 prob 不进搜索结果）。

- 输入「蒲公英 5g + 槐米 3g」→ 摘要显示「2 味药材中，有 1 味在 HERB 数据库有记录，1 味未找到（槐米）」。

## 缺陷清单（按严重度排序）

### [P1] 自定义鉴方对 71 味目录药材报「未找到」——本地明明有完整成分/靶点数据

**复现步骤：**
1. 进入「茶罐 → 自定义鉴方」
2. 添加「槐米」（或「灵芝」「天麻」「蒲公英」等新药材中 HERB search 搜不到的）
3. 点「分析这个方子」，等待约 10-25 秒

**预期：** 本地 shiyang.db 有这味药的完整成分/靶点数据（179 个成分 + 靶点，来源 HERB），应该正常展示分析结果。

**实际：** 显示「1 味未找到（槐米）」，走联网兜底（AI 网页整理），完全浪费了本地已有的结构化数据。

**证据：**
- 直接调用 HERB search API `{func_name:'search_api', keyword:'槐米', label:'Herb'}` → 返回 0 条结果
- 本地 `shiyang.db` 中 `herb` 表有槐米（id=imp:槐米，来源 herb.ac.cn HERB002472），`rel_herb_compound` 有 179 个成分关联
- 代码 `herb_service.py:get_herb_detail` 流程：缓存 → HERB search 拿 id → HERB detail 拉成分。**没有本地库 fallback**
- GUI 截图：`gui-test-screenshots/ux_t4c_analyze_result.png`

**影响：** 105 味目录药材中约 71 味（71%）在自定义鉴方里查不到，用户输入一个常见目录药材得到「未找到」的反馈，严重削弱「数据扩容到 105 味」的实际价值。自定义鉴方是面向用户的核心功能之一。

### [P2] 药材详情弹窗「含预测入血概率与靶点数据」为虚假承诺（69 味新药材的成分全部无 prob）

**复现步骤：**
1. 进入「药材」页，点击「槐米」（或任何 2019/2023/2024 批次新药材，以及 2002 批中 HERB 来源的药材）
2. 查看「成分数据」区块

**预期：** 如实告知用户这味药的成分数据状态——有 X 个成分，其中 Y 个有入血概率预测。

**实际：** 文案写「关联 179 个活性成分，**含预测入血概率与靶点数据**」——但这 179 个成分的 `prob_cctcm` 全为 NULL，靶点也走 v3 表关联不上。

**证据：**
- 截图：`gui-test-screenshots/ux_t2c_huaimi_popup.png`
- SQL 验证：`SELECT COUNT(*) FROM rel_herb_compound r JOIN compound c ON c.id=r.compound_id WHERE r.herb_id='imp:槐米' AND c.prob_cctcm IS NOT NULL` → 0
- 代码：`Herbs.vue` 第 108 行硬编码文案「含预测入血概率与靶点数据」，不区分药材数据质量
- 影响范围：105 味中仅 24 味（v3 覆盖）有真实 prob，其余 81 味的弹窗都存在此过度承诺

**影响：** 用户点进药材详情看到这个承诺，点「到成分库按来源药材继续查看」跳过去——成分库只显示 96 个带 prob 的成分，找不到这些药材的成分，体验断裂。

**实际：** `GET /api/v1/open/snapshot` 返回 11,338,731 bytes ≈ 10.8 MB。

**证据：** HTTP 实测 Content-Length 11MB。`OpenApi.vue` 第 25 行硬编码「约 1.3 MB」。

**影响：** 低，用户下载一次就知道了。但对流量/时间敏感的用户会有预期差。

### [P3] 方子详情页有 1 处未捕获的控制台报错（Cannot read properties of undefined (reading 'length')）

**复现步骤：**
1. 打开任意方子详情页（#1、#73 均复现）
2. 打开浏览器控制台，看到 1 个 page error

**预期：** 无控制台报错。

**实际：** `TypeError: Cannot read properties of undefined (reading 'length')`，两个方子页各 1 条。推测为某个子组件中对 recipe 相关字段的 `.length` 访问缺少可选链保护（候选：`recipe.constitutions_suitable.length` 等位置，需进一步定位）。

**证据：** Playwright 测试收集的 console/page errors，两个 recipe 页面均触发。

**影响：** 低，页面功能正常使用不受影响。但这是质量信号，且不是本次扩容引入（旧方子也有）。
