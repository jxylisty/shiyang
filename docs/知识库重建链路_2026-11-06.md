### `--profile full` 的替代步骤（研究类放到扩容之后）

`current` 口径把研究类步骤（06–09）放在扩容前、只覆盖旧 165 成分。`full` 口径把它们移到
扩容+回填之后、覆盖全库（含 5,478 个 HBIN 新成分），并重新编号：

| # | 步骤 id | 命令 | 校验 |
|---|---|---|---|
| 10 | `13-applicability` | `compute_applicability.py` | `ad_level` 非空 = 有 SMILES 的成分数（动态比对） |
| 11 | `14-cross-validate` | `cross_validate_independent.py` | `prob_indep` 非空 = 有 SMILES 的成分数（动态比对） |
| 12 | `15-chem-map` | `compute_map_coords.py` | `compound_map` = 有 SMILES 的成分数（当前环境会 SKIP） |
| 13 | `16-chembl` | `fetch_chembl_activity.py [--limit N]` | ≥ 1 行 |

注意：`full` 口径下 `compound_map` / `compound_chembl_activity` 覆盖全库，行数与现库（165 / 465）
**必然不同**——现库这两张表只有旧 165 成分。若目标是"和现库一致"，用默认的 `current`。

### 顺序约束（违反会得到错误结果，不是"轻微差异"）

1. `03-analysis-v1` **必须早于** `10-expand`：v1 读 `rel_herb_compound`（v1 表）。扩容后该表混入 8,905 条新药材关联，v1 分析会把新药材成分算进 73 方，`compound_count` 与现库不符。
2. `04-sync-v3` **必须早于** `17-analysis-v3`：v3 用 `radar_*_gsea` 列，而该列由 sync 创建。
3. `12-backfill` **必须早于** `17-analysis-v3`：回填 53 条 herb_id 后，方子才能连到新药材的成分（实测影响 recipe_analysis 的 herb_count/compound_count）。

## 5. 驱动脚本用法

```bash
# 只看计划（不建任何文件）
python -X utf8 scripts/rebuild_all.py --dry-run

# 复刻 19 表基线（现库 2026-11-06 12:19 口径），跳过 AI 与联网
python -X utf8 scripts/rebuild_all.py \
  --target-dir data/_rebuild_test/core19 --skip-ai --skip-legacy10 --skip-network

python -X utf8 scripts/rebuild_all.py --target-dir data/_rebuild_test/fromzero --skip-ai

# 用已入库历史快照播种（唯一能 100% 复刻现库 recipe_analysis 的方式）
python -X utf8 scripts/rebuild_all.py --target-dir data/_rebuild_test/seed \

# 研究类覆盖全库（慢）
python -X utf8 scripts/rebuild_all.py --target-dir data/_rebuild_test/full \
  --profile full --skip-ai --chembl-limit 50

# 失败后续跑（脚本会打印现成命令）
python -X utf8 scripts/rebuild_all.py --target-dir data/_rebuild_test/core19 \
  --skip-ai --skip-legacy10 --start-at 10-expand --force
```

参数表：

| 参数 | 作用 |
|---|---|
| `--target-dir` | 沙箱目录；库最终在 `<dir>/root/data/shiyang.db` |
| `--dry-run` | 只打印资源检查 + 步骤计划，不建文件不执行 |
| `--skip-ai` | 跳过 `pregen_ai_reports` / `pregen_plain`（无 key / 无网关时） |
| `--skip-network` | 跳过需联网且无本地缓存的步骤（如 Enrichr 通路富集） |
| `--skip-legacy10` | 跳过 c99bdd3 的 10 味补录 → 停在 **19 张业务表** |
| `--profile current\|full` | current=研究类步骤放扩容前（复刻现库）；full=放扩容后（全库，慢） |
| `--from-source` | 直接用当前修复版大创库（138 成分），不复刻现库 165 基线 |
| `--seed-from <path>` | 用历史快照播种（`data/shiyang.db.bak-before-rebuild` 等） |
| `--start-at <id>` / `--force` | 续跑 |
| `--continue-on-optional` | 可选步骤失败时继续（默认任何失败都停） |
| `--chembl-limit N` | 传给 `fetch_chembl_activity.py` |

### 生产方式与安全边界

- **沙箱镜像**：`<target>/root/scripts/*.py` + `<target>/root/backend/app/**` + `<target>/root/data/*`；
  外部资源复制到 `<target>/my-asthma-system/...` 等**兄弟目录**。
  脚本里的 `Path(__file__).resolve().parent.parent` 因此指向 `<target>/root`，生产库不在任何路径上。
- **不使用"备份现库 → 原地跑 → 还原"**：那仍存在"删库后失败、还原脚本本身失败"的窗口。沙箱没有这个窗口。
- **禁止把 `--target-dir` 指到 `data/` 本身**，脚本会硬拒。
- `build_db.py` 的 `OUT.unlink()` 在沙箱内执行，删的是 `<target>/root/data/shiyang.db`。

## 6. 已知坑（全部实测踩到）

### 6.1 `build_db.py` 是删库脚本
源码第 20-21 行：
```python
if OUT.exists():
    OUT.unlink()
```
且只建 11 表。**任何文档都不应再让人"先跑 build_db.py 看看"。**

### 6.2 `pregen_analysis_v3.py` 不建表
它直接 `INSERT OR REPLACE INTO recipe_analysis`，表不存在时报
`sqlite3.OperationalError: no such table: recipe_analysis`。
必须先跑 `pregen_analysis.py`（建表）——这也是链路里保留 v1 步骤的唯一原因。

### 6.3 UMAP 环境不兼容 —— 用专用环境 `.venv-rebuild` 解决（2026-11-06 已修）

**症状**（base 环境的 Anaconda Python，sklearn 1.4.2）：
```
TypeError: check_array() got an unexpected keyword argument 'ensure_all_finite'
```
`umap-learn 0.5.12` 硬要求 `scikit-learn>=1.6`（该形参 1.6 起才有）。

**为什么单开环境而不是升级 base**：
- 后端运行时**完全不依赖** sklearn/umap/numpy —— `backend/requirements.txt` 只有
  fastapi/uvicorn/pydantic/httpx/bcrypt/python-jose；用到这些库的只有 4 个离线脚本；
- base 是 Anaconda 共享环境（全机项目共用），且其 tensorflow 已损坏（DLL 初始化失败），
  说明该环境本身在漂移，不该在其上做 sklearn 1.4→1.9 的大版本变更。

**做法**（一次性，仓库内，`.venv-rebuild/` 已在 .gitignore）：
```bash
uv venv .venv-rebuild --python 3.12
uv pip install --python .venv-rebuild/Scripts/python.exe --index-url https://pypi.tuna.tsinghua.edu.cn/simple -r scripts/requirements-rebuild.txt
```
> PyPI 直连在本网络会 TLS handshake eof，必须走镜像源。

**实测结果（2026-11-06）**：

| 项 | base（anaconda） | .venv-rebuild |
|---|---|---|
| numpy / sklearn | 1.26.4 / 1.4.2 | 2.2.6 / 1.9.1 |
| umap-learn | 0.5.12 | 0.5.12 |
| `compute_map_coords.py` | ✗ TypeError，`08-chem-map` 被 SKIP | ✓ 跑通，`compound_map` 产出 **4,558 行** |
| `cross_validate_independent.py` | — | ✓ 导入通过 |
| `compute_applicability.py` / `fetch_chembl_activity.py` | — | ✓ 导入通过 |

`compound_map` 从 165 行扩到 4,558 行是**扩容带来的真实增量**（4,558 个成分带 SMILES），
不是算法变化；UMAP `random_state=42` 确定性经二次重跑验证（坐标逐位相同）。
注意：4,393 个扩容成分的 `prob_cctcm` 为 NULL，前端着色需按「无入血预测」处理——
**2026-11-06 已落地**：`ChemMap.vue` / `MiniChemMap.vue` 对 NULL 用中性灰 `#c9c1b4`，
不再落入「<0.5 偏低」的红色档（那会把「没测」误读成「测了但很低」）；全图页改 canvas 渲染
（4,558 个 SVG circle 会拖死手机），预览卡用 `?max_points=700` 确定性抽样并进视口才请求，
后端一并上 GZip（全量响应 596 KB → 76 KB）。

> 缓存可复现性补充（2026-11-06）：`data/cache/herb_ingest_*.json` 原为 gitignore，
> 一旦丢失且 HERB 接口变动就无法重建扩容数据。现以 gzip 形式入库
> （`data/herb_ingest_*.json.gz`，共 2.6 MB），由 `scripts/_cache_seed.py` 在缺文件时自动还原。

**`rebuild_all.py` 的配套改动**：
- 新增 `--python` 参数；**未显式指定时自动优先用 `.venv-rebuild/Scripts/python.exe`**（存在即用）
- UMAP 预检改为**用目标解释器跑子进程实测**（原先在父进程 import，会出现
  「装了好环境却仍被跳过」的假阴性）
- `--python` 路径不存在时报错并退出码 2（已实测）

### 6.4 `import_herbs` 会覆盖旧药计数
它在写库末尾执行：
```sql
UPDATE herb SET compound_count = (SELECT COUNT(*) FROM rel_herb_compound WHERE herb_id = herb.id)
```
对 32 味 `ccTCM` 旧药，这与 `check_consistency` 的三口径（ccTCM→v3+补录表）冲突，
实测 31 行偏差（乌梅 3→4、佛手 11→6 等）。生产库是事后用 `check_consistency --apply` 修的。
链路必须显式包含 `12b-recount`。

### 6.5 通路富集条数不稳定
同一库连跑两次 `pregen_pathways.py`：58 行 vs 61 行（Enrichr 结果与 `insufficient` 判定会变）。
校验只能要求"≥1 行"，不能写死条数。

### 6.6 现库 `recipe_analysis` 有 13 行无法用当前源数据复算
现库 69 行分析里，17 行的 `radar_summary` 无 `gsea_covered` 键（v1 口径），
其中 13 行的 `top_targets` / `top_compounds` 与"用当前源库重算"不同。
根因：这些行是 2026-10-26 用**修复前**的 `prob_cctcm` 算的（例：柚皮素现库存 0.76，
现源库为 0.5372；十五酸现库 0.98 vs 0.9783）。当前源数据里没有那些旧值。
→ 想 100% 复刻只能 `--seed-from data/shiyang.db.bak-before-rebuild`（该快照在 git 里）。
